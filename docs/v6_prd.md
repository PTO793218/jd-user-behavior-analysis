# AI 电商运营分析工作台 V6 产品需求文档

## 一、问题背景

电商运营人员需要持续判断流量是否被有效承接、用户在哪些环节流失、哪些商品或类目应优先优化、评论负面问题集中在哪里，以及诊断结果如何转化为后续运营动作。当前常见分析方式依赖人工查询、静态报表、单点图表或离线 notebook，业务人员很难在一个连续工作流中获得可解释、可追溯、可执行的结论。

大模型能够降低问数和解释门槛，但如果没有结构化指标工具、统一口径、证据链和风险约束，回答容易泛化、夸大或脱离真实数据。对于运营诊断场景，用户不只需要“一个看起来合理的回答”，还需要知道回答基于哪些数据、调用了哪些工具、可信度如何、哪些结论不能过度解读。

V6 要解决的问题是：让电商运营人员在一个工作台内，通过自然语言完成运营诊断、短期趋势判断、实验方案设计和分析报告沉淀，同时保证结论来自可复现的数据工具、明确的数据口径和可检查的证据链。

## 二、产品目标与成功指标

### 2.1 产品目标

V6 的目标不是做通用聊天机器人，也不是替代完整 BI 系统，而是提供一个面向电商运营诊断的 AI 数据分析工作台。它要把“提问、路由、计算、解释、可视化、追问、报告”串成一个完整工作流。

核心目标包括：

- 降低运营人员提出数据问题和理解分析结果的门槛。
- 将大模型回答约束在真实工具结果、知识库口径和样本边界之内。
- 把分散的指标、图表、证据和建议统一组织为可复盘的运营分析结果。
- 支持从问题诊断自然延伸到 A/B 测试方案和 Markdown 报告沉淀。
- 在模型不可用或证据不足时仍保持系统可信，而不是生成伪结论。

### 2.2 成功指标

V6 上线或演示时，应重点观察以下指标：

- **问题完成率**：典型运营问题能够返回可读回答、工具结果、证据摘要和可信度说明。
- **工具命中率**：典型问题能够路由到正确分析能力，例如路径分析、运营矩阵、评论语义、RFM、价格带、预测或 A/B 方案。
- **证据覆盖率**：关键结论能够关联到结构化工具结果、语义样本或知识库来源。
- **边界说明覆盖率**：涉及评论样本、预测和实验方案的回答必须包含限制说明。
- **报告生成成功率**：已完成的会话能够生成包含结论、证据、建议和限制的 Markdown 报告。
- **降级可信度**：模型不可用时，系统能够保留本地工具结果，并明确不生成模型分析回答。

### 2.3 演示验收目标

面向课程、答辩或项目演示时，V6 至少要完成以下闭环：

1. 用户输入一个自然语言运营问题。
2. 系统识别问题意图并选择合适分析工具。
3. 系统展示业务回答、结构化工具结果和可视化组件。
4. 系统解释为什么调用这些工具，并展示关键证据。
5. 系统在样本、预测或实验类场景中明确说明限制。
6. 用户连续追问时，系统能够利用会话上下文。
7. 用户能够将当前会话生成 Markdown 报告。

## 三、目标用户与使用场景

### 3.1 目标用户

**一线电商运营人员**

关注流量承接、转化流失、商品/类目优化、评论问题和短期活动排期。该角色希望用自然语言快速定位问题，并获得可执行建议。

**数据分析协作人员**

关注指标口径、工具结果、数据来源和证据链。该角色希望系统输出结构稳定，便于校验、复盘和继续开发。

**产品或项目答辩人员**

关注产品完整性、差异化、演示路径和可信边界。该角色需要清晰展示“AI 如何与确定性数据工具结合”，而不是只展示聊天效果。

**系统维护人员**

关注模型配置、降级策略、接口稳定性、异常处理和前后端契约一致性。该角色需要系统在模型失败、工具失败或上下文不足时仍可控。

### 3.2 核心使用场景

**运营诊断场景**

运营人员希望知道当前流量是否被有效承接，转化损失发生在浏览、加购、购买还是复购环节，并找到优先处理对象。

**商品与类目优化场景**

运营人员希望比较商品或类目在流量、转化、销售额和价格带上的表现，识别高流量低转化、低流量高转化等运营机会。

**评论问题诊断场景**

运营人员希望理解质量、物流、售后、包装、价格等评论问题的主要分布，并知道这些结论来自语义样本而不是全量评论统计。

**用户分层经营场景**

运营人员希望比较不同 RFM 用户层的行为差异，用于设计召回、留存、复购和高价值用户运营策略。

**短期趋势判断场景**

运营人员希望查看未来 24 小时销售额基线趋势，用于短期排期参考，但不将其误解为长期经营预测。

**实验方案设计场景**

运营人员希望把诊断结论转化为 A/B 测试目标、假设、分组、指标、周期和风险控制方案。

**分析沉淀场景**

运营人员或数据分析协作者希望把当前会话沉淀为 Markdown 报告，保留问题、结论、证据、工具链路、建议和限制。

## 四、产品定位与差异化

V6 的定位是“AI 辅助的电商运营分析工作台”。它与常见替代方案的差异如下：

- 相比普通 BI：V6 降低提问门槛，支持自然语言追问，并能把指标结果解释成业务建议。
- 相比通用 AI 聊天：V6 的回答必须绑定本地指标工具、知识库口径和证据摘要，不能脱离数据自由发挥。
- 相比静态报表：V6 支持围绕同一问题连续追问、生成实验方案并沉淀报告。
- 相比单点图表工具：V6 将问题识别、工具调用、可视化、可信度、Agent Trace 和报告生成整合到同一工作流。

V6 的核心价值来自四个约束：

- 大模型负责理解问题、规划工具和组织表达。
- 本地工具负责计算确定性指标和结构化结果。
- 知识库负责解释字段、指标口径、数据范围和策略边界。
- 前端负责把回答、证据、工具结果和限制说明以业务用户可读的方式展示。

## 五、产品范围与优先级

### 5.1 P0 必须交付

P0 是 V6 可用闭环，缺失后产品无法成立。

- 三栏式运营分析工作台。
- 自然语言提问和会话展示。
- 典型运营问题的工具路由。
- 本地指标工具返回结构化结果。
- 业务回答基于工具结果生成。
- 工具结果可视化展示。
- 可信度、路由解释和关键证据摘要。
- 评论样本、短期预测、实验方案的限制说明。
- 模型不可用时的可信降级。

### 5.2 P1 优先交付

P1 是增强可信度、演示效果和业务闭环的重要能力。

- Agent Trace 展开查看。
- Markdown 报告生成与预览。
- A/B 测试方案生成。
- 多轮追问上下文摘要。
- RAG 来源展示。
- 原始工具结果折叠查看。

### 5.3 P2 后续迭代

P2 不影响 V6 主闭环，可放入后续版本。

- 正式回答质量评估集。
- PDF 或 Word 报告导出。
- 多数据集切换。
- 矩阵、路径、价格带和预测结果的筛选、排序和导出。
- 更完整的 Agent 可观测性，包括模型耗时、工具耗时、工具命中率和失败原因。
- 在线部署、监控、告警和定时任务。

## 六、核心用户流程

### 6.1 评论语义诊断流程

**用户输入**

用户提出类似“最近差评主要集中在哪些问题”“质量和物流哪个问题更严重”的问题。

**系统动作**

系统识别为评论语义诊断问题，调用语义联动能力，读取已有去重评论语义样本，提取问题分布、代表性证据和限制说明。

**输出结果**

系统返回评论问题概览、主要问题类别、运营建议、样本边界、可信度和可视化结果。

**验收要求**

回答必须明确说明当前语义结果来自 960 条去重评论样本，不代表全量评论统计。

### 6.2 转化与运营矩阵诊断流程

**用户输入**

用户提出类似“哪些商品流量高但转化差”“哪些类目应该优先优化”的问题。

**系统动作**

系统识别为运营矩阵或转化诊断问题，调用类目/商品分析能力，计算流量、转化、销售额等指标，并按象限组织结果。

**输出结果**

系统返回高流量低转化、低流量高转化等对象列表，展示矩阵可视化，并给出优先级建议。

**验收要求**

系统不能只给自然语言判断，必须展示可检查的结构化结果或图表 payload。

### 6.3 用户路径诊断流程

**用户输入**

用户提出类似“用户主要在哪一步流失”“浏览到购买之间的路径有什么问题”的问题。

**系统动作**

系统调用用户路径分析能力，计算常见行为路径、路径转化、流失路径和浏览到购买间隔。

**输出结果**

系统返回关键路径、流失环节、可能原因和后续运营动作。

**验收要求**

关键结论必须能够追溯到路径或漏斗类工具结果。

### 6.4 短期销售预测流程

**用户输入**

用户提出类似“未来 24 小时销售额走势如何”“明天活动排期是否有风险”的问题。

**系统动作**

系统调用短期销售额基线预测能力，输出未来 24 小时趋势和辅助判断。

**输出结果**

系统返回趋势判断、关键时间段、排期建议和预测限制。

**验收要求**

回答必须明确说明这是短期基线趋势辅助判断，不是长期经营预测。

### 6.5 A/B 测试方案流程

**用户输入**

用户提出类似“针对浏览到加购流失设计一个 A/B 测试方案”的问题。

**系统动作**

系统基于诊断结果生成实验目标、假设、实验组、对照组、核心指标、周期、分流、成功标准和风险控制。

**输出结果**

系统返回结构化 A/B 测试方案，并标注方案依据和限制。

**验收要求**

输出必须被明确标记为“实验方案”，不能表述为已完成实验或已证明提升。

### 6.6 报告沉淀流程

**用户输入**

用户在完成一轮或多轮分析后点击或请求生成报告。

**系统动作**

系统读取当前会话、工具调用结果、关键证据、RAG 来源和限制说明，生成 Markdown 报告。

**输出结果**

报告包含分析问题、关键结论、工具链路、证据摘要、数据依据、运营建议和风险限制。

**验收要求**

报告不能只包含模型回答摘要，必须保留工具链路和关键证据。

## 七、界面与交互要求

### 7.1 工作台总览

首屏必须是可操作的运营分析工作台，而不是营销页或普通聊天页。工作台采用三栏结构：

- 左侧为历史会话、高频问题入口和示例问题。
- 中间为运营分析对话、回答卡片、可信度、路由解释、Agent Trace 和输入区。
- 右侧为工具结果可视化、RAG 来源和 Markdown 报告预览。

### 7.2 回答展示

助手回答应呈现为业务分析卡片，而不是普通聊天气泡。回答至少包含：

- 结论摘要。
- 关键证据。
- 运营建议。
- 可信度说明。
- 限制说明。
- 可展开的工具或证据详情。

### 7.3 工具结果展示

工具结果默认以业务可读组件展示，包括指标卡、表格、图表、矩阵、引用和方案摘要。原始工具结果可以折叠保留，供数据分析协作者复盘。

### 7.4 Agent Trace 展示

Agent Trace 可展开查看，但不应抢占主回答。Trace 应展示：

- 本轮问题意图。
- 选择的工具。
- 选择原因。
- 规划方式。
- 模型状态。
- 关键证据。
- 降级或异常信息。

### 7.5 报告预览

右侧面板应支持 Markdown 报告预览。报告预览应强调结论、证据、建议和限制，而不是展示原始 JSON。

## 八、功能需求与验收标准

### 8.1 自然语言运营问答

**需求**

用户可以用自然语言提出运营问题，系统返回业务可读的分析回答。

**验收标准**

- 典型问题能够被识别为明确分析意图。
- 回答必须引用工具结果或证据摘要。
- 对上下文不足的问题，系统应提示补充信息或降低可信度。

### 8.2 工具路由与本地指标计算

**需求**

系统根据问题意图选择合适工具，并由本地指标工具计算确定性结果。

**验收标准**

- 路由结果应能解释为什么选择这些工具。
- 工具结果应返回稳定结构，支持前端渲染。
- 工具失败时应返回可理解错误，而不是生成无依据回答。

### 8.3 用户路径分析

**需求**

系统支持常见行为路径、路径转化、流失路径和浏览到购买间隔分析。

**验收标准**

- 回答应指出关键路径和主要流失环节。
- 右侧证据区应展示路径或漏斗相关结果。
- 建议应围绕流失环节展开，而不是泛泛提出运营建议。

### 8.4 运营矩阵分析

**需求**

系统支持按流量和转化对类目或商品划分象限。

**验收标准**

- 输出应包含至少四类象限解释。
- 高流量低转化对象应给出优先优化建议。
- 低流量高转化对象应给出放量或曝光建议。

### 8.5 评论语义联动分析

**需求**

系统支持基于已有去重评论语义样本分析质量、物流、售后、价格、包装或内容体验问题。

**验收标准**

- 必须说明语义样本边界。
- 不能把样本结论描述为全量评论统计。
- 应展示问题类别、占比或排序，以及代表性证据摘要。

### 8.6 RFM 行为差异分析

**需求**

系统支持比较不同 RFM 用户层的行为和偏好差异。

**验收标准**

- 输出应区分不同用户层。
- 建议应匹配用户层特点，例如召回、留存、复购或高价值运营。
- 不得将 RFM 分层解释为用户真实身份标签。

### 8.7 价格带转化分析

**需求**

系统支持按价格区间统计浏览、购买、销售额、转化和用户层分布。

**验收标准**

- 输出应展示不同价格带的核心指标。
- 建议应说明适合优化、放量或谨慎处理的价格区间。
- 不能脱离数据直接给出调价结论。

### 8.8 短期销售预测

**需求**

系统支持未来 24 小时销售额基线预测和趋势判断。

**验收标准**

- 必须标注为短期基线预测。
- 必须说明不适合作为长期经营预测。
- 预测建议应是排期参考，而不是确定性承诺。

### 8.9 A/B 测试方案生成

**需求**

系统支持基于诊断结果生成 A/B 测试方案。

**验收标准**

- 方案应包含目标、假设、实验组、对照组、核心指标、周期、分流、成功标准和风险控制。
- 必须明确这是实验方案，不是实验结果。
- 不得声称已经证明转化提升。

### 8.10 Markdown 报告生成

**需求**

系统支持将当前会话生成 Markdown 报告。

**验收标准**

- 报告应包含问题、结论、工具链路、关键证据、数据依据、RAG 依据、运营建议和风险限制。
- 报告应保留样本、预测或实验类能力的限制说明。
- 报告内容应面向复盘和汇报，而不是简单复制聊天记录。

### 8.11 模型不可用降级

**需求**

模型不可用时，系统仍应尽可能计算本地工具结果。

**验收标准**

- 系统可以展示工具结果和可视化。
- 系统不能生成伪模型分析回答。
- 界面应明确提示当前处于降级状态。

## 九、用户故事

1. 作为电商运营人员，我希望用自然语言提出经营问题，以便不写 SQL 或 Python 也能完成运营分析。
2. 作为电商运营人员，我希望查看最常见的用户购买路径和流失路径，以便定位转化损失发生在哪些环节。
3. 作为电商运营人员，我希望识别高流量低转化的类目或商品，以便优先优化详情页、价格、促销或选品策略。
4. 作为电商运营人员，我希望了解评论问题主要集中在哪些方面，以便判断质量、物流、售后、价格、包装或内容体验的优化优先级。
5. 作为电商运营人员，我希望评论相关回答明确说明样本边界，以便不把语义样本误认为全量评论统计。
6. 作为电商运营人员，我希望比较不同 RFM 用户层的行为差异，以便设计差异化留存、召回和增长策略。
7. 作为电商运营人员，我希望比较不同价格带的浏览、购买、销售额和转化表现，以便判断哪些价格区间更适合重点运营。
8. 作为电商运营人员，我希望查看未来 24 小时销售额趋势，以便将短期历史趋势作为运营排期参考。
9. 作为电商运营人员，我希望预测结果明确说明限制，以便不把短周期基线预测误解为长期经营预测。
10. 作为电商运营人员，我希望系统能基于诊断结果生成 A/B 测试方案，以便把浏览到加购流失等问题转化为可执行实验。
11. 作为电商运营人员，我希望 A/B 测试内容被明确标记为实验方案，以便不误认为系统已经完成真实线上实验。
12. 作为电商运营人员，我希望在工具结果区看到图表、表格、矩阵和方案摘要，以便不用阅读原始 JSON 也能检查证据。
13. 作为电商运营人员，我希望展开 Agent Trace，以便理解本轮问题意图、选择工具、规划方式、模型状态和关键证据。
14. 作为电商运营人员，我希望每次回答后能看到可信度和路由解释，以便判断回答来自确定性指标、语义样本、RAG 片段还是有限证据。
15. 作为电商运营人员，我希望能在同一会话中连续追问，以便不必每次重复完整上下文。
16. 作为电商运营人员，我希望系统在追问缺少上下文时提示补充信息，以便避免系统编造结论。
17. 作为电商运营人员，我希望能把当前会话生成 Markdown 报告，以便保留分析结论、证据链、工具结果和限制说明。
18. 作为数据分析协作人员，我希望工具结果结构稳定，以便前端能一致渲染表格、图表、矩阵、引用、方案和报告。
19. 作为产品或技术协作人员，我希望系统区分结构化行为数据、RFM 数据、语义样本和知识库内容，以便每个结论都能追溯到正确证据来源。
20. 作为系统维护人员，我希望模型不可用时仍能计算本地工具结果，但不生成伪模型分析，以便系统在降级状态下仍保持结果可信。
21. 作为项目演示人员，我希望系统有稳定的示例问题和演示路径，以便完整展示问答、证据、Trace 和报告闭环。
22. 作为数据分析协作人员，我希望报告保留限制说明，以便后续复盘时不会误读样本、预测或实验方案。

## 十、实现决策

### 10.1 模块划分

**前端工作台模块**

负责三栏式运营分析工作台，管理会话、发送问题、渲染回答、展示可信度、路由解释、Agent Trace、工具结果、RAG 来源和报告预览。

**后端 API 模块**

负责概览、聊天、会话管理、报告生成、语义摘要和知识库检索接口，并将 Agent 原始结果标准化为前端可稳定展示的响应结构。

**会话存储模块**

负责保存会话、消息和工具调用结果，支持历史会话、会话详情、最近上下文、工具调用记录和会话删除。

**Agent 编排模块**

负责问题意图识别、工具规划、工具执行、证据摘要、模型回答、模型不可用降级和异常处理。模型可用时优先由模型规划工具；规划失败或模型不可用时使用保守规则兜底。

**指标与诊断工具模块**

负责计算数据概览、漏斗、用户路径、运营矩阵、语义联动、RFM 差异、价格带、销售预测和 A/B 测试方案。该模块应返回摘要、表格、图表数据和口径说明，而不是只返回自然语言。

**知识库检索模块**

负责检索项目背景、字段定义、指标口径、数据范围、样本限制和运营策略解释。知识库用于补充解释和边界说明，不替代结构化指标计算。

**证据与可解释模块**

负责生成可信度、路由解释、关键证据摘要和 Agent Trace，说明系统用了什么、为什么用这些工具、结论由哪些证据支撑。

**报告生成模块**

负责基于当前会话生成 Markdown 报告。报告应包含分析问题、关键结论、Agent 工具链路、关键证据摘要、数据依据、RAG 依据、运营建议和风险限制。

### 10.2 接口契约

聊天响应需要提供稳定字段：

- `answer`：面向业务用户的运营分析回答。
- `tools`：按工具名称组织的结构化工具结果。
- `visual_payloads`：适合前端渲染的图表、表格、矩阵、引用、指标卡和方案摘要。
- `rag_sources`：用于解释背景或口径的知识库片段。
- `routing_explanation`：本轮为什么选择这些工具。
- `confidence`：可信度等级和原因。
- `context_summary`：多轮追问使用的上下文摘要。
- `evidence_summary`：从工具结果中提取的关键业务事实。
- `agent_trace`：意图、规划工具、规划原因、规划方式、模型状态和关键证据。

概览响应需要提供顶部运营指标、趋势图数据、语义样本说明和模型配置状态，但不能暴露密钥。

报告响应需要返回当前会话生成的 Markdown 文档。

### 10.3 数据模型决策

会话存储需要支持三个概念实体：

- **会话**：用户可见的对话容器，包含标题和时间信息。
- **消息**：归属于会话的用户消息和助手消息。
- **工具调用**：与助手消息关联的工具名称和序列化工具结果。

保留工具调用记录的目的是支持会话报告生成、追问上下文构建和人工复盘，而不必每次重新计算全部结果。

### 10.4 Agent 工作流决策

Agent 工作流如下：

1. 接收用户问题和可选会话上下文。
2. 判断问题是独立问题还是追问。
3. 模型可用时，优先让模型按严格格式规划工具。
4. 工具规划失败或模型不可用时，使用保守规则选择工具。
5. 执行本地分析工具，读取结构化数据和已有语义结果。
6. 从工具输出中生成关键证据摘要。
7. 检索必要的知识库口径、字段解释或策略边界。
8. 让模型基于关键证据、完整工具结果和 RAG 来源生成业务分析回答。
9. 返回标准化结果，包括回答、工具、可视化 payload、可信度、路由解释、证据摘要和 Agent Trace。

模型不可用时，系统仍应计算并展示本地工具结果，但不能生成伪模型分析回答。

## 十一、数据说明与可信边界

### 11.1 数据类型

V6 使用的数据可分为以下类型：

- **结构化行为数据**：用于计算浏览、加购、购买、路径、漏斗、价格带和销售额等指标。
- **RFM 数据**：用于比较不同用户价值层的行为差异。
- **评论语义样本**：用于分析评论问题分布和代表性问题。
- **知识库内容**：用于解释字段、指标口径、数据范围、样本限制和运营策略。

### 11.2 数据边界

- 结构化行为数据是历史数据，不是实时生产数据。
- 评论语义分析基于已有去重样本，不能描述为全量评论统计。
- 销售预测是未来 24 小时短期基线趋势辅助判断，不是长期经营预测。
- A/B 测试输出是实验方案，不是已完成实验结果。
- 知识库用于解释定义、口径和策略，不扫描行为明细。
- 系统不得把缺失数据、样本偏差或模型推断包装成确定性结论。

### 11.3 可信度定义

**高可信**

结论主要来自确定性结构化指标，且工具结果完整、口径明确、无明显样本限制。

**中可信**

结论来自结构化指标和语义样本或 RAG 解释的组合，适合辅助判断，但需要注意样本范围或业务假设。

**低可信**

问题缺少上下文、工具结果不足、样本限制明显或模型处于降级状态。系统应提示用户补充条件或只展示可确认结果。

## 十二、AI 回答质量与风险控制

### 12.1 回答原则

- 先引用证据，再给出判断。
- 先说明数据边界，再给出建议。
- 能用工具结果回答的问题，不用模型自由推断替代。
- 证据不足时给出低可信提示，而不是补全不存在的事实。
- 涉及预测、实验和样本时，必须主动说明限制。

### 12.2 证据优先级

回答生成应遵循以下证据优先级：

1. 本地结构化指标工具结果。
2. 工具结果中的关键证据摘要。
3. 评论语义样本结果。
4. 知识库字段、口径和策略解释。
5. 模型基于上述材料组织的业务表达。

模型不得用第五类内容覆盖前四类证据。

### 12.3 禁止表达

系统回答中不得出现以下表达方式：

- 将评论语义样本描述为全量评论统计。
- 将未来 24 小时基线预测描述为长期经营预测。
- 将 A/B 测试方案描述为已经执行的实验。
- 声称某个方案已经证明提升转化率或销售额。
- 在工具失败或无数据时给出确定性业务结论。
- 暴露模型密钥、内部配置密钥或不应展示的系统信息。

### 12.4 异常与低可信处理

- 上下文不足时，系统应提示需要补充的条件。
- 工具失败时，系统应说明失败模块和可继续查看的结果。
- 知识库无结果时，系统可以继续基于结构化工具回答，但不能伪造来源。
- 模型不可用时，系统只能展示本地工具结果和降级提示。

## 十三、非功能需求

### 13.1 性能

- 普通运营问题应在可接受时间内返回首屏回答和关键工具结果。
- 复杂工具组合可以分阶段展示，先返回可用结果，再补充完整证据区。
- 报告生成应避免阻塞主问答流程。

### 13.2 稳定性

- 模型失败、工具失败、知识库无结果和上下文不足都必须有明确状态。
- 前端不得因为单个工具结果缺失而导致整页不可用。
- API 字段应保持向后兼容，避免前后端契约漂移。

### 13.3 可维护性

- 工具输出结构应稳定，便于前端组件复用。
- 新增工具时应同步补充路由说明、可视化 payload 和验收用例。
- 知识库口径更新不应要求修改问答主流程。

### 13.4 安全与隐私

- 概览和模型状态可以展示配置是否可用，但不能暴露密钥。
- 日志应避免记录敏感配置。
- 当前 V6 不处理多租户、企业权限和生产级用户隔离。

## 十四、测试决策

### 14.1 好测试的标准

测试应通过公开模块契约和 API 响应验证行为，而不是验证私有实现细节。关键测试应证明：

- 典型业务问题能路由到预期分析能力。
- 确定性指标工具返回稳定结构化结果。
- 模型不可用时系统不生成伪分析回答。
- 模型回答输入中包含关键证据摘要。
- API 响应包含前端展示所需字段。
- 工具结果能生成可视化 payload。
- 报告包含工具链路和关键证据。
- 涉及样本、预测和实验的能力能说明限制。

### 14.2 测试范围

**指标工具测试**

- 验证用户路径、运营矩阵、语义联动、RFM 差异、价格带、销售预测和 A/B 方案的返回结构。
- 验证预测和语义能力返回口径说明或限制说明。

**Agent 测试**

- 验证典型业务问题命中预期工具。
- 验证模型不可用时仍返回工具结果，但不生成伪分析回答。
- 验证关键证据摘要会进入模型分析输入。
- 验证 Agent Trace 包含规划工具和模型状态。

**API 测试**

- 验证健康检查和概览响应结构。
- 验证会话创建、查询、删除和详情获取。
- 验证聊天响应包含回答、工具、可视化 payload、可信度、路由解释、证据摘要和 Agent Trace。
- 验证使用知识库时返回 RAG 来源。
- 验证报告生成包含工具链路和证据章节。
- 验证缺少上下文的追问返回低可信度和补充提示。

**前端构建测试**

- 验证 TypeScript 和生产构建通过。
- 用于发现 API 响应契约和前端类型之间的漂移。

**人工验收测试**

- 提问质量诊断问题，确认回答说明语义样本边界。
- 提问运营矩阵问题，确认右侧出现矩阵可视化。
- 提问未来 24 小时销售额趋势，确认回答说明短期预测限制。
- 提问 A/B 测试方案，确认输出是实验方案而非实验结果。
- 展开 Agent Trace，确认可看到意图、工具、规划方式和关键证据。
- 生成 Markdown 报告，确认报告包含结论、证据、建议和限制。

## 十五、发布与演示策略

### 15.1 V6 发布形态

V6 默认面向本地项目演示和课程答辩场景，不承诺生产级在线部署。系统使用固定项目数据和已有知识库完成完整演示闭环。

### 15.2 演示路径

推荐演示路径如下：

1. 展示工作台总览和顶部核心指标。
2. 输入评论诊断问题，展示样本边界和语义证据。
3. 输入运营矩阵问题，展示工具结果可视化和优先级建议。
4. 输入未来 24 小时销售额趋势问题，展示短期预测限制。
5. 输入 A/B 测试方案问题，展示实验方案结构。
6. 展开 Agent Trace，说明工具规划和证据来源。
7. 生成 Markdown 报告，展示分析沉淀能力。

### 15.3 演示准备要求

- 准备覆盖评论、矩阵、预测、A/B 和报告的示例问题。
- 确认模型可用状态和降级状态均有可解释表现。
- 确认右侧证据区在典型问题下有稳定展示内容。
- 确认报告内容包含结论、证据、建议和限制说明。

## 十六、范围外内容

V6 不包含以下能力：

- 接入实时生产数据。
- 执行真实线上 A/B 实验。
- 声称实验结果或已证明提升。
- 长期销售额预测。
- 重新清洗原始数据。
- 重新运行评论语义分析。
- 将评论语义样本视为全量评论统计。
- 用户权限、多租户或企业账号管理。
- 在线部署、监控、告警或定时任务。
- 自动执行价格调整、活动创建、库存调整等运营动作。
- 面向用户的任意新数据集上传与接入流程。
- PDF 或 Word 报告导出。
- 完整回答质量基准评估集。

## 十七、后续迭代方向

后续迭代应优先围绕评估、导出、数据扩展和可观测性展开：

- 建立正式回答质量评估集，覆盖期望工具、必须口径说明和禁止表达。
- 增强报告导出格式，支持 PDF 或 Word。
- 为矩阵、路径、价格带和预测结果增加筛选、排序和导出能力。
- 支持多数据集切换。
- 增强 Agent 可观测性，记录模型耗时、工具耗时、工具命中率和模型失败原因。
- 建立演示问题集和标准验收脚本，降低每次展示前的人工检查成本。

## 十八、PRD 维护原则

维护本 PRD 时，应描述稳定的产品行为、模块职责、接口契约和验收标准，避免写入容易过期的代码路径、行号或实现片段。

当数据范围、样本数量、模型能力或接口契约发生变化时，应优先更新以下内容：

- 数据说明与可信边界。
- 功能验收标准。
- AI 回答质量与风险控制。
- 发布与演示策略。
- 范围外内容和后续迭代方向。
